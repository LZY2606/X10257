# Analysis: deterministic chain from schema dependencies to multi-language generated code

This document describes the real execution chain that turns `.skir' schema
files into generated code for every supported language, and pins down the
invariants that make the generated bytes deterministic. Every statement is
anchored to a file and line in this repository. The regression material
lives in `src/generation_determinism.test.ts` and runs as part of
`npm test`.

## 1. Call chain

The public entry points are unchanged. The chain is:

1. **Module collection** — `collectModules` (`src/module_collector.ts:11`)
   globs `skir-src/**/*.skir` (`src/module_collector.ts:40`), reads every
   file, and builds the `modulePath → content` map. Editable modules are
   layered on top of already-compiled dependency packages
   (`src/module_collector.ts:16-24`).
2. **Compilation (linking)** — `ModuleSet.compile`
   (`src/module_set.ts:50`) is the single public entry used by the CLI
   (`src/compiler.ts:131-136`), by the formatter and by the snapshotter.
   Per module it runs:
   - **Tokenizer** — `tokenizeModule` (`src/tokenizer.ts:26`) turns source
     text into tokens. Called from `src/module_set.ts:143`.
   - **Parser** — `parseModule` (`src/parser.ts:43`) turns tokens into a
     `Module` with unresolved type references. Called from
     `src/module_set.ts:163`.
   - **Import processing & cycle detection** — imports are resolved
     depth-first with an `inProgressSet`; a cycle produces the user error
     "Circular dependency between modules" (`src/module_set.ts:190`), a
     missing file produces "Module not found" (`src/module_set.ts:205`),
     and a broken dependency produces "Imported module has errors"
     (`src/module_set.ts:227`).
   - **Symbol linking** — three ordered loops
     (`src/module_set.ts:268`, `src/module_set.ts:279`,
     `src/module_set.ts:295`): (1) every record is registered in the
     cross-module `recordMap`, (2) every field type is resolved by
     `TypeResolver.resolveRecordRef` (`src/module_set.ts:1147`), (3) field
     recursivity and doc references are resolved.
   - **Finalization** — `finalize` (`src/module_set.ts:909`) detects
     duplicate method numbers (`src/module_set.ts:939`) and duplicate
     record numbers (`src/module_set.ts:963`) across modules, then
     aggregates per-module errors in module insertion order.
3. **Generation** — `WatchModeMainLoop.doGenerate`
   (`src/compiler.ts:175`) calls each language plugin through the public
   `CodeGenerator.generateCode` interface (`src/compiler.ts:194`) with
   `modules` (in `ModuleSet` insertion order) and the shared `recordMap`.
   Two generators emitting the same path is a hard error
   (`src/compiler.ts:202-204`).
4. **Write-out** — files are written per output path and stale files are
   removed in reverse-sorted order (`src/compiler.ts:225-265`).

## 2. Symbol identity

- A record's identity is its `RecordKey`, computed as
  `"<modulePath>:<position of the record name>"` (`src/parser.ts:468`),
  with an extra suffix for inline records (`src/parser.ts:469-471`).
  Identity therefore includes the module path — two records with the same
  name in different modules or different nesting levels are always
  distinct symbols and can never be confused by the linker.
- All cross-module state lives in `DeclarationRegistry`
  (`src/module_set.ts:1389`), merged per module
  (`src/module_set.ts:268-277`, `src/module_set.ts:394`) and exposed
  read-only through `ModuleSet.recordMap` (`src/module_set.ts:1005`).
- Because the key embeds a character position, editing a file (even
  adding a blank line) produces fresh keys. Keys are therefore an
  internal, per-compilation identity: they are consistent within one
  `ModuleSet`, and generators must resolve them through `recordMap`
  instead of serializing them (see risk R1 below).

## 3. Cross-file references

- Imports are resolved to module paths by the parser; the linker loads
  imported modules recursively (`src/module_set.ts:186-198`).
- A type reference such as `other_module.Outer.Zoo` is resolved by
  `TypeResolver.resolveRecordRef` (`src/module_set.ts:1147`): it walks
  from the most nested enclosing record outwards
  (`src/module_set.ts:1175-1189`), then the module's top-level
  declarations (`src/module_set.ts:1192`), then follows `import` /
  `import-alias` declarations into the imported module
  (`src/module_set.ts:1230-1280`). Re-exports are rejected
  ("Cannot refer to imports of imported module"), so a reference always
  binds to the module that defines the record.
- The resolution result stored on each field is the target record's
  `RecordKey`, so the dependency graph between records is exactly the
  set of keys reachable through resolved field types.

## 4. Error recovery

- User errors are data, not exceptions: they are collected as
  `SkirError` values carrying the offending token (module path, line,
  column) and are surfaced through `ModuleSet.errors`
  (`src/module_set.ts:1009`). A rejected compilation still returns a
  complete, self-contained `ModuleSet`; no shared state is half-updated.
- Incremental recompilation is the only cache: `ModuleSet.compile`
  accepts the previous `ModuleSet` (`src/module_set.ts:52`), and watch
  mode passes the previous set — including a failed one — back in
  (`src/compiler.ts:135-138`). The cache's version identity is the exact
  source text of each module (`src/module_set.ts:1346-1352`): a module
  bundle is reused only if its content is byte-identical *and* every
  transitive dependency is also reused; otherwise it is downgraded to
  tokens-only and re-linked (`src/module_set.ts:1355-1377`). A failed
  compilation therefore cannot poison the next run: reused bundles are
  bit-identical to what a clean compile would produce, and the cache is
  discarded after construction (`src/module_set.ts:101`).
- `ModuleSet` is immutable after construction; there are no module-level
  counters, singletons or temp files in the compile/generate path, so no
  state can leak from one invocation to the next.

## 5. Output ordering

- `ModuleSet.modules` iterates in input-map insertion order
  (`src/module_set.ts:96-101`); on the CLI path that order comes from the
  sorted glob of source files (`src/module_collector.ts:40`).
- Generators receive modules in that order (`src/compiler.ts:195`) and
  emit one file set per module; the compiler keys outputs by path
  (`src/compiler.ts:206`), so the final artifact set is a
  `path → bytes` map whose content does not depend on module order.
- Generated bytes for a given module depend only on that module's
  resolved model and the shared `recordMap` — not on parse order, cache
  state, or generator scheduling. This is what
  `src/generation_determinism.test.ts` proves for the TypeScript, Go,
  Python and Rust generators.

## 6. Risks that would cause drift or mis-binding

- **R1 — leaking positional identity into output.** `RecordKey` embeds a
  character position (`src/parser.ts:468`). A generator that serializes
  raw keys (instead of names resolved through `recordMap`) would produce
  different bytes when only whitespace/newlines shift positions.
- **R2 — order-sensitive aggregation.** Module and error iteration
  follow input insertion order (`src/module_set.ts:96-101`,
  `src/module_set.ts:985-994`). A generator that concatenates
  cross-module content (index files, registries) in iteration order
  without canonicalizing would drift under file-order permutation.
- **R3 — stale cache reuse.** The incremental cache's version identity
  is exact source text plus transitive dependency reuse
  (`src/module_set.ts:1346-1377`). Reusing a bundle whose dependency
  changed, or mutating a `ModuleSet` after construction, would bind
  fields to stale record identities or leak state between invocations.

## 7. Regression material

`src/generation_determinism.test.ts` enters exclusively through the
public entries (`ModuleSet.compile` and each plugin's
`CodeGenerator.generateCode`) and covers, with minimal inputs:

- file input order permutation (all 6 permutations of 3 modules);
- same record name across namespaces (binding to distinct identities);
- import reference cycles (positioned, reproducible rejection, then
  recovery with the failed `ModuleSet` reused as cache);
- unknown type references (positioned, reproducible rejection);
- field/record number conflicts (first violation reported with
  module/line/column);
- newline-only differences (LF vs CRLF, blank lines) — generated bytes
  stay identical even though internal positional identities shift;
- irrelevant conditions: cache state, generator invocation order and
  repeated runs — including proof that a successful run carries no
  cache, counter or temporary state left behind by an intervening
  failure.
